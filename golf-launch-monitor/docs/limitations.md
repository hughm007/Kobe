# Limitations

**Document date:** 2026-10-01. **Applies to:** `golf-launch-monitor-0.1.0` with physics
`glm-physics-0.1.0-provisional`, ground model `glm-ground-0.2.0-provisional`, terrain
`glm-terrain-0.2.0`, shot simulator `glm-shot-sim-0.1.0` and estimator `glm-launch-fit-0.1.0`.
Each shot records the versions it used.

This document lists what the software **cannot** tell you. The status vocabulary is defined in
[product-requirements.md §1](product-requirements.md#1-status-vocabulary); phase numbers follow
the [phase plan](product-requirements.md#9-phase-plan). Model details are in
[physics-model.md §12](physics-model.md#12-limitations) and [terrain-model.md §9](terrain-model.md#9-limitations).

## The short version

1. **No hardware has measured anything.** Every launch value this build produces is synthetic,
   a replay of synthetic data, typed in by a developer, estimated, assumed, or unavailable.
2. **Nothing is VERIFIED.** Test agreement means one of three things, none of them real-world
   evidence:
   - agreement with synthetic truth generated by the same physics model;
   - agreement with closed-form mechanics;
   - agreement with public averages or common-knowledge targets that were used to choose the
     parameters.
3. **Uncertainty intervals exclude model error.** They sample launch velocity and spin only. They
   do **not** include aerodynamic or ground-model error, environment uncertainty or ball-to-ball
   variation. A narrow interval is not an accurate number.
4. **Confidence values are heuristic policy scores.** They are not probabilities and are not
   statistically calibrated against reality. Launch-data confidence and flight-model confidence
   answer different questions (see [Confidence scores](#confidence-scores)).
5. **Total distance is more model-dependent than carry.** The ground model is provisional, and
   driver rollout lands in its plausibility envelope only because a putting-speed relation is
   extrapolated to fairway roll speeds.

## No measurement exists yet

| Fact | Consequence |
|---|---|
| The camera, radar and hybrid adapters are placeholders. `connect()`, `startCapture()` and `calibrate()` throw `HardwareNotAvailableError`; health is always `disconnected`. | No genuine hardware measurement can exist in Phase 1. A hand-made replay file can still *claim* camera data, and its provenance is only as good as its author. |
| `datasets/raw-shots/`, `datasets/reference-measurements/` and `datasets/calibration/` are empty. The only dataset is a synthetic replay (`datasets/synthetic/range-fixtures.jsonl`) plus its golden summary. | No accuracy statistic (bias, RMSE, …) exists for any metric. `@glm/validation` is ready to compute them but has no data. |
| No calibration procedure exists (Planned, Phase 2). Shots record `calibrationVersion: "uncalibrated"`. | The calibration factor scores 1.0 for synthetic and manual data because those data do not pass through a sensor. Live or replayed hardware data without calibration would be rejected. |
| Stereo vision, ball detection and trigger hardware do not exist (Planned, Phase 2); spin measurement from images does not exist (Planned, Phase 3). | Ball-at-address, hitting-zone and trigger checks run only on flags that the synthetic or manual adapter generates. |

## Sensors and data sources

- **Synthetic truth uses the simulator's own physics.** `createTruthPropagator` and the launch
  fit both use `propagatePositions` from `@glm/ballistics`. Recovering synthetic launch
  conditions therefore tests the estimator and the uncertainty bookkeeping. It does not test
  whether the physics matches real balls.
- **Synthetic noise settings are test settings, not device models.** The default is 1000 fps,
  20 frames, 1 mm position sigma, perfect clock sync, an ideal trigger and honestly reported
  covariance. Confidence on a synthetic shot reflects these settings. In the golden dataset,
  clean synthetic shots come out `valid` with launch-data confidence ≈ 0.99. The data-origin
  banner ("SYNTHETIC DATA — generated for testing, not measured.") is what tells the user the
  shot is not real.
- **`spinMode: "measured"` is not a provenance label.** It means "taken from a spin observation
  that passed the quality gate". On a synthetic stream that observation is synthetic, and the
  value's `source` is `synthetic`; on a developer manual stream it is `manual`. Read provenance
  from `source` and the badge, never from `spinMode`.
- **Developer manual entry.** The manual adapter emits typed-in spin as a spin observation with
  `method: "synthetic"` and the flag `manual-entry`. Its count and residual fields are
  placeholders (10 and 0), not quality statistics, so typed spin up to the gate's 15 000 rpm cap
  always passes the quality gate. On a manual stream `resolveSpin` keeps the label `manual`, so
  launch values and spin show MANUAL. Manual shots are always `provisional` and never eligible
  for scoring.
- **Manual launches without spin** are propagated with zero spin over the 10 ms window.
- **Replays of real hardware** are supported by the `glm-replay-1` format, but none exist. Replay
  files and JSON exports must match this build's format, schema and coordinate-system versions
  exactly. There is no migration path yet.
- **Replay files carry no player or club.** The replay CLI processes them with no player and no
  club (right-handed labels; no club-prior spin estimate is possible). The desktop UI attributes
  replayed shots to the player, handedness and club of its current Setup, and the shot card
  says so. Neither is a record of who actually hit the shot.
- **Hardware stub capabilities** (e.g. `measuresSpin: true`) describe what the sensor *class* is
  specified to provide. They do not describe any device.

## Launch-state estimation

- **Thresholds are provisional engineering choices with no reference data behind them.** The
  fit-quality ramps:
  - RMS residual: 3 mm good, 20 mm poor;
  - velocity sigma: 0.2 m/s good, 1.5 m/s poor;
  - χ²/dof: 4 good, 9 poor;
  - inlier fractions.

  The trigger-agreement tolerance (3 ms) and the 10 ms trigger cluster window are also
  provisional.
- **The drag- and lift-aware refit uses the resolved spin.** With unavailable spin it assumes no
  Magnus lift and says so in a warning. With estimated spin, the refit inherits that estimate's
  error.
- **Trigger fusion.** Per-source latency must be supplied by the caller; no device latencies are
  known. Triggers more than 10 ms after the first one but inside the 0.5 s shot window (for
  example the ball hitting the screen) are kept as evidence and reported in a warning; they do
  not move the impact time and never open a new shot. A genuine second impact source arriving
  more than 10 ms late (a slow sensor whose latency was not configured) is treated the same way.
- **Club-delivery data** (club speed, path, face, attack angle, …) is always `unavailable`.
  Planned (Phase 4).

## Spin

- **Spin measurement is not implemented** (Planned, Phase 3). Every spin value comes from one of
  these sources:
  - synthetic data;
  - developer entry (labeled manual, see above);
  - a club prior;
  - the player's history;
  - a user-allowed generic fallback.
- **Club priors are a poor predictor for amateurs.** Per-category totals are seeded from widely
  published TrackMan PGA Tour averages (driver 2686 rpm … pitching wedge 9304 rpm).
  - Tour players differ from a garage golfer in speed, attack angle, strike quality and ball.
    Hence the 35 % sigma, confidence 0.25, and the `estimated-club-model` label.
  - The categories are coarse: a 5-iron and a 7-iron share the `mid-iron` prior (the mean of
    5-, 6- and 7-iron). There is no putter prior.
  - Research for this project could not confirm these tour values on the source page. They are
    *secondary source, not verified on page*, and the older-table driver spin figure in
    particular could not be confirmed.
- **No spin axis from a prior or the fallback.** Zero tilt is assumed for simulation.
  - Curve is withheld (shown as unavailable).
  - Offline values assume no curve, and their confidence is multiplied by 0.6.
  - A real slice or hook in that mode is simulated as straight.
- **The player-history model is unreachable in Phase 1.** It needs at least 5 *measured* shots of
  the same club category within ±15 % ball speed, and no measured shots exist. Range sessions
  also pass an empty history.
- **The generic fallback is the same rule for every club.** It uses spin parameter S = 0.15
  (|ω| = 0.15·|v|/r) with a 50 % sigma and confidence 0.1, and it is off by default. It says
  nothing about the actual shot.
- **Near-zero spin.** A noisy spin vector near 0 rpm has a magnitude biased upward. With the
  default synthetic noise the mean is about 91 rpm. The spin axis is reported as unavailable.
- **Quality-gate thresholds are provisional:** ≥ 4 rotation observations, residual ≤ 0.06 rad,
  relative sigma ≤ 15 %, ≤ 15 000 rpm.

## Air-flight physics

Details and numbers are in [physics-model.md](physics-model.md).

- **The aerodynamic coefficients are provisional.** They were chosen so that two public
  tour-average launches (driver and 7-iron; *secondary source, not verified on page*) land inside
  a plausibility envelope. That check is a **sanity envelope, not validation**: the same averages
  chose the parameters, and parameter sets whose C_D and C_L differ by about 5–10 % pass it
  equally well.
- **Drag and lift are both below the cited wind-tunnel sources, and the two errors offset in
  carry.** Quantities that depend on drag and lift separately are unvalidated, for example wind
  response and landing speed.
- **Profiles 2–4 share profile 1's aerodynamics.** `two-piece-distance-baseline`,
  `range-ball-practice` and `generic-fallback` use exactly the parameters of
  `premium-urethane-baseline`. They differ only in confidence ceiling and warnings. Range and
  limited-flight balls are likely to fly shorter than simulated.
- **Not modeled:**
  - reverse Magnus (negative lift at low Re and low spin);
  - spin-axis precession (the axis keeps its world direction; only the magnitude decays);
  - ball orientation, seam or dimple-pattern effects;
  - wind gradients and gusts.
- **The moment of inertia is the uniform-sphere value.**
- **Applicability ranges:** 25–85 m/s and 1000–10 000 rpm. Re and S are checked only at the
  start of each flight segment. Knuckleballs, high-spin wedges (S > 0.4), chips and putts are
  outside the supported range and produce warnings.
- **Determinism holds on one JavaScript engine.** Last-bit differences across engines are
  possible (`Math.exp` and `Math.pow` are implementation-approximated).

## Ground model and total distance

Ground model v0.2 (`glm-ground-0.2.0-provisional`) adds a crater-tilted impact and a
speed-dependent rolling resistance. [terrain-model.md](terrain-model.md) documents it, with its
known biases.

- **Total, bounce and roll depend on the provisional ground model.** It has no fitted
  parameters: restitution, friction, rolling resistance, crater size and firmness are judgements.
  Expect totals to change between ground-model versions.
- **Driver rollout reaches the sanity envelope only through an extrapolation.** The
  speed-dependent rolling-resistance term comes from a green relation reported for putting
  speeds (*secondary source, not verified on page*; its unit is inferred, not read). It is
  applied to every surface and to roll speeds up to 16.5 m/s (the knuckleball's roll-phase
  start), bounded by the sliding friction. Without it the fixture drives would run 57–66 yd instead of 33–38 yd
  ([terrain-model.md §7.3](terrain-model.md#73-plausibility-envelope-a-sanity-check-not-validation)).
  Nothing measured supports the term at fairway speeds, and the envelope targets themselves are
  common knowledge, not a sourced dataset.
- **Spinless low shots keep skipping.** A fast, shallow landing with little or no spin leaves
  each grazing impact almost without speed loss along the tilted crater plane, so it skips a long
  way. The synthetic knuckleball (93 yd carry) runs about 83 yd on the ground, and with drag-free
  hops a softer surface makes it run *farther*. This is a known limitation pinned by tests
  (`packages/ground-physics/test/plausibility-envelope.test.ts`, "KNOWN LIMITATION …"); a
  ploughing loss that would fix it has no data to size it.
- **Steep landings.** Above the crater-angle clamp (about 61° on a green at 25 m/s) a steeper
  landing finishes slightly less far behind its pitch mark (also pinned as a known limitation).
- **Total is more model-dependent than carry.** It inherits every air-model error plus every
  ground-model error. Ground metrics carry a 0.75 confidence factor, and the simulator warns
  "total is more model-dependent than carry".
- **The surface is simulated, not observed.** Range sessions simulate landing on a flat virtual
  fairway (`fairway-normal`). In a garage the real ball hits a screen; there is no observed
  landing, bounce or roll.
- **Bounce and roll are signed along-track displacements** along the landing heading
  ([coordinate-system.md §5](coordinate-system.md#5-derived-flight-metrics)). A ball that spins
  back gives negative values; sideways kicks are excluded.
- **Not modeled:** hole and cup capture, flagstick, tree canopy, bunker lips, grain, plugging,
  and wet-turf dynamics.

## Environment

- **Defaults:** 20 °C, 50 % relative humidity, 101 325 Pa (sea level), indoor, no wind. Each
  default is recorded with `fieldSource: "default"`.
- **Indoor defaults do not lower confidence.**
  - Defaulted fields are flagged (`environment-defaulted:…`), but the 0.9 confidence factor
    applies only outdoors.
  - Example: in a garage at 1600 m with altitude and pressure left at default. The model itself
    predicts about 4.6 % more driver carry at 1600 m than at the sea-level default
    ([physics-model.md §9](physics-model.md#9-plausibility-envelope--a-sanity-check-not-validation)),
    so the reported carry is short by roughly that much (by the model's own, unvalidated,
    sensitivity).
  - Enter measured station pressure where possible.
- **Pressure derived from altitude** assumes the ISA standard temperature profile. A weather
  report's sea-level pressure is not station pressure.
- **Air model simplifications:** ideal-gas moist air; humidity ignored in viscosity; wind
  uniform and steady. Wind is rejected in indoor mode.

## Uncertainty and confidence

**Monte Carlo intervals (p05–p95)**

| Included | Not included |
|---|---|
| Launch velocity, sampled from its fit covariance; launch spin vector, sampled from its covariance (measured, estimated or assumed) | Aerodynamic and ground **model and coefficient** error; environment uncertainty; ball-to-ball variation; launch-position uncertainty; systematic sensor or club-prior bias |

Details: [architecture.md §5](architecture.md#5-uncertainty-propagation).

- **The intervals exclude model error.** A narrow interval can still be wrong. Example: the
  golden synthetic straight driver has a 90 % carry interval about 1.3 m wide (≈ 1.4 yd), so it
  is shown as a single number. The physics behind it is only known to sit within the ±6 %
  plausibility envelope (about ±15 m of the target carry), and other parameter sets also pass
  that envelope.
- **Coverage is tested on synthetic data only.** On synthetic data with honestly reported noise,
  1σ launch intervals cover the truth about 68 % of the time and the 90 % carry interval covers
  the true carry in most trials (`tests/integration/uncertainty-calibration.test.ts`). With a
  real sensor whose reported noise is wrong, coverage is unknown. The fit inflates the
  covariance by χ²/dof but does not fix a systematic bias.
- **Estimated spin has an assumed, isotropic spread.** For club-prior and generic-fallback spin
  the spin covariance is σ²·I, with σ = 35 % or 50 % of the spin rate in every direction. The
  Monte Carlo therefore samples an assumed spread of spin rate, spin-axis tilt and rifle spin.
  Those intervals describe the assumption, not the shot.
- **Few samples, noisy percentiles.** The default range-session count is 100 samples, so p05 and
  p95 are themselves noisy. A metric's interval is dropped unless at least max(10, half the
  samples) succeed. With 0 samples (the library default) no intervals are produced.
- **Monte Carlo uses a coarser integration.** The air and hop timestep is at least 4 ms
  (`MONTE_CARLO_MIN_TIMESTEP_S`, vs 1 ms for the reported trajectory), with at least 1 s output
  sampling. In a spot check on the seven fixtures (2026-10-01, ground model v0.2) carry and
  total changed by less than 0.001 mm. This is not covered by a test. The reported value comes
  from the 1 ms trajectory, not from the Monte Carlo p50.

### Confidence scores

- **Two confidences, two questions.**
  - **Launch-data confidence** (`LaunchState.overallConfidence`; "Launch data" on the shot card)
    scores how well the launch values were obtained from this stream: fit quality, sensor
    health, calibration, trigger, ball at address and spin quality. On synthetic data it
    describes the internal consistency of generated data, not accuracy.
  - **Flight-model confidence** (`ShotResult.simulationConfidence`; "Flight model" on the shot
    card) scores how far the calculated flight and roll can be trusted: it is capped by the ball
    profile's ceiling (0.4–0.6, because the aerodynamics are unfitted) and by the spin's own
    confidence. Each calculated metric has its own confidence with further factors (ground
    × 0.75, assumed axis × 0.6).
  - A shot can therefore show "Launch data: High · 99%" next to "Flight model: Medium · 60%".
    Neither number is validated against real shots.
- **Every number is a policy value. None is calibrated against reality.**
  - Validity thresholds: 0.35 (invalid) and 0.7 (valid).
  - The factor weights and score ramps.
  - Spin confidences: 0.25 club prior, 0.5 player model, 0.1 generic, 0.57–0.95 observed.
  - Ball-profile ceilings: 0.4–0.6.
  - Factors: ground × 0.75, assumed axis × 0.6, defaulted outdoor environment × 0.9.
  - Labels: high ≥ 0.8, medium ≥ 0.5.
- **A confidence is not a probability.** 0.6 does not mean a 60 % chance of anything. Two shots
  with equal confidence can have very different real errors.
- **Calculated metrics can never be labeled "high".** The ball-profile ceiling is at most 0.6.
- **A clean synthetic launch value can be labeled "high".** That describes the internal
  consistency of generated data, not accuracy.
- **Unavailable spin has weight 0 in the aggregate,** by design. A launch with no spin can
  therefore score higher overall than one using the generic fallback; it simulates nothing,
  while the fallback asserts a generic value.

## Definitions and display

- **Carry is to first ground contact.** It ends when the ball center is one radius from the
  virtual ground ([coordinate-system.md §5](coordinate-system.md#5-derived-flight-metrics)). Some
  devices define carry to launch height. `@glm/validation` refuses to compare the two unless the
  caller asserts, per shot, that our first contact was within ±0.05 m of launch height.
- **Horizontal launch is +left internally.** That is the opposite of many commercial displays.
  The UI shows `L`/`R`, and exports name the column `horizontal_launch_deg_left_positive`.
- **The shot-shape label uses spin-axis tilt only.** ±2° is straight; more than 12° is hook or
  slice. It ignores start direction (a push-fade and a pull-fade are both "fade"), and the
  thresholds are display conventions, not standards.
- **Range sessions default to right-handed.** With no player selected, `createRangePipelineConfig`
  uses `handedness: "right"`, so a left-handed golfer's draw and fade labels are swapped until the
  player is selected. The physics is unaffected.
- **Backspin and sidespin are display-only.** They are the components of the spin perpendicular
  to the flight direction, |ω⊥|·cos(tilt) and |ω⊥|·sin(tilt)
  ([coordinate-system.md §4.3](coordinate-system.md#43-launch-direction-frame-and-spin-axis-tilt)),
  are never stored, and carry no range. The definition text in the metric detail panel still
  reads "totalSpin · cos(spinAxis)"; the two agree unless the ball has rifle spin.

## Storage and export

- **Data is stored unencrypted on the local machine.** Browser data lives in IndexedDB under the
  browser profile; the Node backend writes JSON files. If the browser offers no IndexedDB the UI
  keeps shots in memory only and says that nothing survives a reload.
- **Clearing the browser's site data deletes all shots.** There is no backup or sync; use the
  CSV/JSON export.
- **Deleting a player while keeping their shots** leaves those shots referencing the deleted
  player id. Shot records are immutable evidence and are never rewritten.
- **The UI deletes players and sessions only.** Deleting a single shot or clearing everything
  exists in the repository API but has no UI control yet.
- **JSON import accepts only the current schema and coordinate-system versions.**
- **Shot ids are assigned at processing time,** not at capture. Re-processing a recording with a
  different id provider, or in a different order, gives different ids; reference pairing and the
  hash-based train/validation/held-out partitions would then move. When building validation
  datasets, partition by a capture-derived key (for example the recording's content hash plus
  the shot's capture index) rather than by the processing-time `shotId`
  ([validation-protocol.md §3.3](validation-protocol.md#33-pairing)).

## What the tests do not show

- **Golden tests detect change, not correctness.** They pin the model's own output to 1e-9
  relative.
- **The plausibility-envelope tests are circular** (see Air-flight physics and Ground model).
- **The UI tests run in jsdom,** not in a real browser: layout, legibility at garage distance,
  the real Web Worker and real IndexedDB are not exercised (a fake worker object and an
  in-memory repository stand in).
- **Some code has no automated test:** the refit-failure fallback in `processShot`; the
  × 0.75 / × 0.6 / × 0.9 metric-confidence factors; out-of-bounds and penalty-area penalties; the
  UI's IndexedDB selection, delete-session control and Shot review screen; the absence of network
  calls (checked by inspection; production builds add a Content-Security-Policy).
